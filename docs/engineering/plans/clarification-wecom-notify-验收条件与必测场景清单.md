# clarification-wecom-notify 验收条件与必测场景清单

- 任务：clarification-wecom-notify
- 日期：2026-11-06
- 用途：后续开发声明 e2e、代码评审核对覆盖、测试与部署逐条验证的编号来源
- 数据准备现状：AutoWonder 测试库未配置在 `jiuji_dev_db` 可用库列表中；以下场景均需在具备测试环境与账号后执行。

## 验收条件

### 验收 1：新提问推送站内通知

- 现象：工单澄清会话新增待回答提问后，每位人类参与人收到一条站内通知。
- 前置：`workitem.id=W1`；`agent_conversation.id=C1`（`channel=WORKITEM_CLARIFICATION`、`biz_ref_type=WORKITEM`、`biz_ref_id=W1`）；参与人 U1 至 U5 均为人类且 `in_app=1`；数字人 `agent=10035`。
- 动作：数字人提交 elicitation，`request_id=TEST-CWN-R1`、`message=请确认验收范围`。
- 可观测结果：`notification` 中 `ref_type=WORKITEM AND ref_id=W1 AND type=WORKITEM_INPUT_REQUIRED` 行数 `=` 5；每行 `title` `=`「需求澄清待回答」；每行 `content` `⊇`「请确认验收范围」；`link` `~` `^/workitems/W1\?.*panel=clarify.*conversation=C1`。
- 维度：正向。
- 覆盖层级：接口+DB。
- 覆盖用例：S1、T01。
- 数据可复用：否（写入通知数据）。
- 数据准备：需造（W1、C1、T1、U1 至 U5）；需提供（测试环境、5 个人类账号、1 个数字人账号）。

### 验收 2：重复投递不重复通知

- 现象：同一 elicitation 请求重复投递时，不新增提问行，也不新增通知。
- 前置：已存在 `request_id=TEST-CWN-R1`、`status=PENDING`。
- 动作：以同一 `request_id` 再次提交 elicitation。
- 可观测结果：`agent_conversation_elicitation` 中该 `request_id` 行数 `=` 1；对应 `notification` 行数保持不变 `=` 5。
- 维度：并发。
- 覆盖层级：接口+DB。
- 覆盖用例：S2、T02。
- 数据可复用：否（依赖验收 1 的数据）；下游 e2e 场景须写 `depends_on: 验收 1`，不可单独重跑。
- 数据准备：复用验收 1 的数据。

### 验收 3：非工单澄清会话不推送

- 现象：普通数字人会话中的 elicitation 不产生待回答通知。
- 前置：`agent_conversation.id=C2`、`channel=AGENT_DIRECT`、`biz_ref_type=null`。
- 动作：在 C2 提交 elicitation。
- 可观测结果：`notification` 中与 C2/该请求关联的行数 `=` 0。
- 维度：逆向。
- 覆盖层级：接口+DB。
- 覆盖用例：S3。
- 数据可复用：是。
- 数据准备：需造（C2、T2）；需提供（测试环境、数字人账号）。

### 验收 4：非 PENDING 状态不推送

- 现象：已回答或已取消的提问不会产生新的待回答通知。
- 前置：`request_id=TEST-CWN-R3`、`status=ANSWERED` 或 `CANCELED`。
- 动作：重复投递或再次 openPending。
- 可观测结果：该 `request_id` 对应 `notification` 行数 `=` 0。
- 维度：逆向。
- 覆盖层级：接口+DB。
- 覆盖用例：S4。
- 数据可复用：是。
- 数据准备：需造（R3 已答/已取消行）；需提供（测试环境）。

### 验收 5：接收人仅人类参与人且跨租户隔离

- 现象：只有工单人类参与人收到通知，非参与者、数字人与其他租户用户均不收到。
- 前置：W1 参与人 U1 至 U5（人类）；数字人 U10 在参与者集合；U9 非参与者；`workitem.id=W2` 属 `tenant_id=2`。
- 动作：分别在 W1、W2 触发澄清提问。
- 可观测结果：W1 通知接收人集合 `=` {U1,U2,U3,U4,U5}；U9、U10 的通知行数 `=` 0；W2 通知行数 `=` 0。
- 维度：权限。
- 覆盖层级：接口+DB。
- 覆盖用例：S5、T05。
- 数据可复用：是。
- 数据准备：需造（U9、U10、W2）；需提供（测试环境、两个租户账号）。

### 验收 6：提问正文超过 200 字截断

- 现象：站内与企业微信消息中的提问正文最多 200 字，超出部分以省略号结尾。
- 前置：`message` 长度 201 与 200 两条提问。
- 动作：分别触发通知。
- 可观测结果：201 字消息的提问部分长度 `=` 201（200 字 +「…」）；200 字消息的提问部分 `=` 原文。
- 维度：边界。
- 覆盖层级：组件层。
- 覆盖用例：S6、T06。
- 数据可复用：是。
- 数据准备：需造（两条不同长度 message）；需提供（测试环境）。

### 验收 7：企微偏好开启才投递，关闭仅站内

- 现象：`WORKITEM_INPUT_REQUIRED` 的企微偏好开启时收到企微消息，关闭时只收到站内通知。
- 前置：U1 `notify_pref.wecom=1`、U2 `notify_pref.wecom=0`，二者均已绑定企微；`selectedProvider=WECOM`。
- 动作：触发 W1 澄清提问。
- 可观测结果：U1 的 IM 队列任务数 `=` 1；U2 的 IM 队列任务数 `=` 0；U1、U2 的站内 `notification` 行数均 `=` 1。
- 维度：权限、正向。
- 覆盖层级：接口+DB、人工。
- 覆盖用例：S7、T07。
- 数据可复用：否（写入偏好与队列）。
- 数据准备：需造（U1/U2 偏好行）；需提供（测试环境、已绑定企微的测试账号）。

### 验收 8：企微深链直达澄清面板

- 现象：企业微信消息中的链接打开对应工单的澄清会话面板。
- 前置：W1、C1、agent 10035，通知已生成。
- 动作：点击企业微信消息中的链接。
- 可观测结果：URL 路径 `=` `/workitems/W1`；查询参数逐项 `⊇` `panel=clarify`、`fullscreen=1`、`agent=10035`、`conversation=C1`；页面展示对应澄清会话（人工）。
- 维度：正向。
- 覆盖层级：页面 e2e、人工。
- 覆盖用例：S8、T08。
- 数据可复用：是。
- 数据准备：需提供（已绑定企微的测试账号、可访问的测试前端）。

### 验收 9：同单双弹允许两条

- 现象：同一工单同时存在 dispatch 待回答与澄清提问时，两条通知各自生成，互不抑制。
- 前置：W1 存在 dispatch INPUT 待回答请求；同时触发澄清提问。
- 动作：分别触发 dispatch 待回答与澄清提问。
- 可观测结果：W1 的 `WORKITEM_INPUT_REQUIRED` 通知行数 `=` 2；两条 `link` 不同（dispatch 默认链接与澄清深链各一条）。
- 维度：一致性。
- 覆盖层级：接口+DB。
- 覆盖用例：S9。
- 数据可复用：否（写入通知数据）。
- 数据准备：需造（dispatch 待回答请求）；需提供（测试环境）。

### 验收 10：既有通知兼容与失败隔离

- 现象：既有 dispatch 待回答通知的链接与投递不受影响；通知监听器失败不影响提问落库与数字人继续。
- 前置：既有 dispatch INPUT 请求；模拟通知监听器内部抛出异常。
- 动作：触发 dispatch 待回答与澄清提问；强制通知失败。
- 可观测结果：dispatch 通知 `link` `=` `/workitems/{id}?workspaceId={tenant}`（无澄清参数）；澄清 elicitation 行存在 `=` 1；`publishEvent` 调用方未收到异常；日志包含失败告警 `⊇`。
- 维度：兼容回归。
- 覆盖层级：组件层、接口。
- 覆盖用例：S10、T10。
- 数据可复用：是。
- 数据准备：需造（dispatch 请求、异常注入）；需提供（测试环境）。
