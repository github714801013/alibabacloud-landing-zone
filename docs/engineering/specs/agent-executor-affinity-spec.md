# 执行器锁定降维：按派发血缘绑定、交付解锁、会话均衡

- 任务标识：`agent-executor-affinity`
- 确认日期：2026-10-29
- 状态：用户已确认，适用于当前分支的本地二次开发
- 依据：用户需求「执行器锁定降维、不锁工单、按 dispatchId 锁定、交付时解除」及 grill 阶段逐项确认（Q1–Q14）

## 问题陈述

现有「工单级执行器亲和」把整张工单锁定到一台执行器（Redis 哈希，TTL 7 天），粒度与真实需求不符：

1. 锁定维度太粗。需求是「按 dispatchId 锁定、交付时解锁」，而现状会在工单生命周期内跨派发、跨步骤强制同机，超出必要范围。
2. 澄清会话被工单绑定拖着走。工单亲和降级换机时，澄清会话被整体迁到新执行器并清空本地 CLI 会话引用，用户的对话上下文静默丢失。
3. 「交付即解锁」在工单维度无法表达。工单随时可能有新的派发，绑定没有一个明确的终点。
4. 新建澄清会话没有分散策略。同一数字人的新会话倾向落在同一执行器，且执行器已有积压时仍继续接收新会话。
5. 执行器满载时缺少可见的排队与上限。会话轮次可能无限排队，用户看不到明确的「繁忙」结论。

## 解决方案

删除工单级亲和，改为「派发血缘 + 会话自身」两级绑定：

- **派发侧**：`dispatch.executor_id` 就是绑定。一个派发一旦选定执行器，打包失败重试仍回到同一台；飞行中的源派发（交互续跑）严格绑定到源执行器；派发进入终态即视为交付、绑定自然失效，后续重试作为新派发重新选机。绑定执行器不可用时进入等待窗口，窗口到期直接失败，不静默换机。
- **会话侧**：澄清会话硬绑自身执行器，满容量排队、离线明确报错；排队有可配置上限。新建会话在选机时排除已有积压的执行器，优先选择最近 48 小时绑定数最少的执行器；全部候选都有积压时选择队列最短的一台。
- **统计**：绑定数与队列深度全部使用 Redis 计数器，不在选机路径上做 SQL 统计，也不新增数据库索引或表结构。

## 实现决策

### 绑定与解锁

- 派发绑定载体就是派发记录上的执行器字段；不新增 Redis 绑定键。
- 非终态退回待办（打包失败、执行器回报忙碌、provider 故障重试、准备阶段重试）均不再清空执行器字段，保证同一派发从选机到终态始终同一台机器。
- 血缘绑定只向上追溯到仍在飞行中的源派发：交互续跑（侧交互、正式交互）严格绑定源执行器；源派发已进入终态即视为已交付，其后的重试/继续/交接作为新派发重新选机。
- 连续会话模式（CONTINUOUS）维持现有严格绑定语义，不在本次调整范围内。
- 绑定执行器不可用（离线、满容量、缺协议特性）时，派发保持待办并记录新的等待原因；等待窗口到期后派发失败，不换机。失败即交付，绑定随之失效。

### 删除清单

- 删除工单亲和存储（Redis 哈希、Lua 脚本、锁、等待起点字段）、工单亲和选机与降级分支、绑定写入。
- 删除工单亲和引入的等待原因与释放点；删除降级时迁移会话的同步组件。
- 删除前端等待原因映射与中英文案；删除降级事件文案。
- 存量 Redis 键不做清理，依赖 7 天 TTL 自然过期。

### 澄清会话

- 会话创建时选定执行器后，此后所有轮次严格使用该执行器，不再读取工单级绑定。
- 绑定执行器在线但无剩余容量时，轮次进入排队而不是报错；执行器离线时返回明确的离线错误。
- 排队轮次重投时必须严格回到会话绑定的执行器，禁止软选机换机。
- 排队上限可配置（默认 30 分钟）：只作用于「等待空闲槽位」的排队，不作用于「等待会话上一轮结束」的排队；起算点是轮次变为可执行的时刻；到期该轮次失败并提示繁忙。

### 新建会话选机

选机顺序为四级：

1. 沿用现有过滤：执行器不可用、无剩余容量、缺协议特性均排除。
2. 排除存在排队轮次的执行器。
3. 剩余候选按最近 48 小时内的绑定数升序取最少（会话改绑时旧执行器扣减、新执行器计入，已解绑的不再统计）；计数相同用现有轮询游标打破平局。
4. 若第 2 级把候选清空，选择队列深度最小的执行器继续排队。

该顺序只作用于新建会话，适用于澄清会话与平台/IM 会话；已有会话的后续轮次不参与重新选机（澄清会话硬绑，平台会话维持其现有软优先语义）。

### Redis 统计

- 绑定计数：按「租户 + 数字人 + 执行器」建计数器，每次新会话绑定到执行器时自增；会话改绑到其他执行器时旧执行器自减、新执行器自增，已解绑的会话不再计入。TTL 等于均衡窗口（默认 48 小时），键只在首次创建时设置 TTL，形成滚动窗口。
- 队列深度：按同一维度的计数器，轮次入队自增、出队（派发/失败/取消/超时）自减；TTL 取排队上限的 2 倍作为漂移自愈上界。
- 读取：对候选执行器批量读取计数，缺键按 0 处理。
- 降级：Redis 不可用或读取异常时跳过排除与排序，退回现有轮询选机并记录告警，不阻塞新建会话。
- 计数器是旁路统计，数据库中的轮次状态仍是唯一事实源；异常路径造成的偏差由 TTL 自愈。

### 配置与文案

- 新增派发绑定等待窗口配置，默认 1,800,000ms（30 分钟）；原亲和等待窗口配置改名，默认值不变。
- 新增会话排队上限配置，默认 1,800,000ms（30 分钟）。
- 新增会话均衡窗口配置，默认 172,800,000ms（48 小时）。
- 新增派发绑定等待原因；删除亲和等待与亲和锁占用等待原因。
- 新增/调整的文案在中英双语资源中成对维护。

### 二次开发组织

- 新增逻辑放在独立新文件：Redis 计数组件、会话准入与均衡组件；不改造成通用框架，不新增抽象层。
- 上游文件只做接入与旧补丁回收，逐文件登记在上方「二次开发改动面」表中。
- 不新增依赖、不改数据库表结构与索引。

## 测试决策

好测试的标准：只通过公开入口验证外部行为，不测试私有方法与实现细节；断言使用独立来源的期望值（固定的计数、固定的候选顺序、固定的失败原因），不按被测代码的算法重算期望值。测试随实现按红→绿推进，每轮只覆盖一个接缝。

| 接缝 | 位置（公开方法） | 覆盖行为 | 先例 |
|---|---|---|---|
| S1 派发调度 | `DispatchService.runPending` | 血缘严格绑定；等待窗口到期失败且不换机；打包回退保留执行器；终态源不传播绑定；连续会话语义不变 | `DispatchServiceRunPendingTest` |
| S2 会话准入 | `WorkitemClarificationConversationService.createConversation` / `submitTurn` | 新建会话排除有排队的执行器；按最近绑定数升序；全部排队时选队列最短；已有会话严格绑定；满容量入队；离线报错；绑定计数自增 | `WorkitemClarificationConversationServiceTest` |
| S3 排队重投 | `AgentConversationService.recoverQueuedTurns` | 严格绑定重投不换机；排队超时失败；队列深度自增与自减 | `AgentConversationServiceTest` |
| S4 计数与排序组件（新增接缝） | 新组件的公开接口 | 缺键按 0；滚动窗口 TTL；排序与平局；全部被排除时的兜底；Redis 异常降级 | `ConversationAdmissionServiceTest`、`ConversationExecutorStatsTest` |

S4 是唯一新增接缝：排除、排序与兜底是纯策略逻辑，若只在 S2/S3 覆盖会被大量 mock 淹没，难以定位失败原因。

## 验收标准

1. 同一派发打包失败重试后仍落在同一执行器。
2. 飞行中的源派发产生的交互续跑严格落在源执行器；源进入终态后的重试可以重新选机。
3. 绑定执行器不可用时派发等待，窗口到期失败且失败原因可观测，不发生换机。
4. 澄清会话创建后固定自身执行器；满容量入队，离线返回明确错误。
5. 排队轮次重投不换机；超过排队上限的轮次失败并给出繁忙提示。
6. 新建会话不会分配到有排队积压的执行器；全部有积压时分配到队列最短的执行器。
7. 绑定计数与队列深度只从 Redis 读取，选机路径无新增 SQL 统计。
8. Redis 不可用时新建会话仍能完成（降级轮询）。
9. 旧的工单亲和代码、等待原因、前端映射与文案全部移除，无残留引用。
10. 定时任务派发行为不变。

## 不在范围内

- 定时任务派发（来源为定时任务运行）的绑定与选机。
- 跨派发、跨步骤的执行器连续性（已明确放弃）。
- 已有澄清会话的自动迁移或自动改绑；执行器删除后的会话恢复需要运维介入。
- 执行器 daemon 侧行为、容量上报口径与容量模型调整。
- 数据库表结构、索引或统计 SQL 的变更。
- 发布到外部议题跟踪器：当前 fork 未启用 Issues，规格先作为本地文档保存，未执行外部写入。

### 已知代价与未核验项

- 已知代价：执行器被删除或不再服务该数字人时，澄清会话会持续返回离线错误，需要运维重建会话兜底（用户明确选择硬绑而非自动改绑）。
- 未核验：执行器 daemon 收到不存在的本地会话引用时的具体行为（不在本仓库）；容量上报口径与并发上限由执行器侧决定，平台只做核算。
- 未核验：计数器在 Redis 故障切换窗口内的短暂偏差影响，按 TTL 自愈处理，不做对账。
