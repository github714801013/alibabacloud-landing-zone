# clarification-wecom-notify 规格

- 任务：clarification-wecom-notify
- 日期：2026-11-06
- 来源：`docs/engineering/plans/clarification-wecom-notify-澄清定稿.md`（用户已确认）
- 二次开发改动面：`docs/engineering/specs/clarification-wecom-notify-customization-points.md`

## 问题陈述

工单需求澄清会话中，数字员工会通过 ACP 提出需要人工回答的问题。当前只有打开澄清页面或站内通知才能发现这些问题，人在企业微信里工作时容易错过，导致澄清停滞、交付等待。

## 解决方案

在工单澄清会话中新落库且处于待回答状态的提问产生时，向工单全部人类参与人发送一条「需求澄清待回答」通知：写入站内通知中心，并按用户现有的企业微信偏好投递企业微信消息；消息中的链接直达对应工单的澄清会话面板。通知失败不影响提问落库与数字人继续，重复投递不产生重复通知。

## 用户故事

1. 作为工单创建人，我希望澄清会话出现待回答问题时收到企业微信提醒，以便及时决策，不必一直盯着工单页面。
2. 作为工单的人类指派人，我希望收到同样的提醒，以便在接手交付前先回答澄清问题。
3. 作为参与过评论或被@的人，我希望在参与过的工单出现待回答问题时收到提醒，以便继续提供信息。
4. 作为人类请求发起人，我希望数字员工反问我时收到提醒，以便补充必要信息。
5. 作为用户，我希望点击企业微信消息后直接打开对应的澄清会话，而不是先落到工单首页再自己找。
6. 作为关闭了企业微信通知的用户，我希望仍然能在站内通知中心看到提醒，不因偏好关闭而完全丢失信息。
7. 作为用户，我希望同一条提问因网络重试或重复投递出现多次时，只收到一条通知。
8. 作为用户，我希望普通数字人会话中的提问不要混入工单待回答通知。
9. 作为用户，我希望已经回答或已取消的提问不再提醒。
10. 作为用户，我希望很长的提问在通知里被截断到可读长度，而不是把整段正文塞进消息。
11. 作为用户，我希望同一工单既有 dispatch 待回答又有澄清提问时，两类提醒都能收到，不互相覆盖。
12. 作为运维人员，我希望通知发送失败只记录日志，不影响提问落库和数字人后续执行。
13. 作为安全负责人，我希望只有同租户的工单人类参与人收到通知，数字人、非参与人和其他租户用户都收不到。
14. 作为维护者，我希望既有 dispatch 待回答通知及其链接保持原样，本次改动不引入回归。
15. 作为 fork 维护者，我希望本次改动集中在少量文件并可独立识别，便于后续同步上游。

## 实现决策

- 在需求澄清提问首次落库时发布领域事件：仅当 `insertIfAbsent` 返回 1、状态为 `PENDING`、会话为工单澄清通道且工单引用非空时发布；事件携带租户、工单、会话、数字人、turn、请求标识与提问正文。
- 通知在事务提交后执行：监听器使用 `AFTER_COMMIT` 与独立事务，先校验工单存在且租户一致，再取人类参与人；无参与人时跳过。
- 通知接收人为工单人类参与人全集，与现有 dispatch 待回答通知口径一致；不按回答权限收窄。
- 复用 `WORKITEM_INPUT_REQUIRED` 通知类型与设置页「工单待澄清」偏好；企业微信默认值不变，仍按用户偏好投递。
- 站内通知与企业微信共用同一份正文；提问正文超过 200 字截断并追加省略号，空或全空白正文不推送。
- 企业微信消息链接使用澄清面板深链，携带 `panel=clarify`、`fullscreen=1`、数字人与会话参数；站内通知链接同源。
- IM 任务增加可选链接字段：本通知携带澄清深链；既有 dispatch/mention 任务不传该字段时继续使用原有工单链接，保持兼容。
- 通知监听器内部捕获运行时异常并记录告警，异常不向事件发布调用方传播。
- 同一工单的 dispatch 待回答与澄清提问各推一条，不做跨事件去重。
- 不改数据库结构、不改对外 API、不改前端页面与交互；仅新增站内通知与 IM 队列运行数据。
- 变更落在 fork 本地可识别的最小范围：新增监听器、事件记录与测试；对上游文件的修改仅为发布点、IM 任务可选链接、格式化回退与双语资源键。

## 测试决策

- 好的测试只验证外部行为：事件是否发布、通知是否生成、接收人是谁、链接与正文是什么、既有链接是否回退；不断言私有方法与内部实现细节。
- 复用现有测试接缝，不新增测试抽象层：
  - 提问发布点：验证新提问发布、重复投递抑制、非澄清通道抑制。
  - 通知监听器：串联监听器到通知服务与 IM 队列，验证类型、文案、深链、接收人、截断与异常隔离。
  - IM 任务序列化：验证新增可选链接字段向后兼容，旧任务缺字段时仍可反序列化。
  - 企业微信格式化：验证有链接时使用澄清深链，无链接时回退既有工单链接。
  - 渠道入队：验证 `WORKITEM_INPUT_REQUIRED` 仍走既有可靠队列路径。
- 先例：`DispatchRequestNotificationListenerTest`、`PlatformImNotifyChannelTest`、`NotifyServiceLocaleTest`、`ImNotificationFormatterTest`、`ImNotificationTaskSerializationTest`。
- 验证命令使用 `mvn -DskipFrontend=true -DskipGitCommitId=true -Dtest=ConversationElicitationServiceTest,WorkitemClarificationQuestionNotificationListenerTest,ImNotificationFormatterTest,ImNotificationTaskSerializationTest,PlatformImNotifyChannelTest test`；前端 `npm run build` 不作为本任务单测前置，避免无关前端构建阻塞。
- 测试数据基线见 `docs/engineering/plans/clarification-wecom-notify-测试数据.md`；测试库未配置时先登记未覆盖，测试阶段回填。

## 不在范围内

- 在企业微信内直接回答问题或操作工单。
- 新增独立通知类型、设置项或改变企业微信默认开关。
- 同一工单多类通知的聚合、跨事件去重或频率限制。
- 修改澄清面板 UI、交互、显隐逻辑或前端路由。
- 数据库结构变更、迁移脚本、对外 API 变更。
- 提交、推送、部署或发布；需用户另行授权。
