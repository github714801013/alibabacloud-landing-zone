# 工单澄清会话评论归属规格

- 任务标识：`conversation-comment-author`
- 确认日期：2026-10-28
- 状态：用户已确认，适用于当前分支的本地二次开发
- 依据：用户原话“应该是实际跟 AI 对话的人”，以及后续明确选择和最终“确认”。

## 问题说明

真人在工单澄清会话中与数字人沟通后，数字人通过会话 MCP 写入工单评论，作者却显示为数字人的创建者。澄清入口已取得当前登录人，但身份没有保存为澄清会话归属人，签发令牌仍使用数字人创建者，造成署名与沟通责任人不一致。

## 解决方案

工单澄清会话第一次有效发言时，将该真人固定为会话归属人。数字人在此会话中使用 MCP 时，以固定归属人的身份执行现有权限允许的操作，工单评论作者随之正确归属。

“实际对话人”按用户选择解释为会话第一次有效发言的人。后续其他真人接着发言、工单改派、执行器重连或轮次重试，都不变更会话归属人。历史上没有归属人的会话，在下一次有效发言时补齐；尚未补齐时保持既有身份回退。

## 用户故事

1. 作为首次发言的真人，我希望澄清数字人的工单评论署在我的账号下，以便评论归属与沟通责任一致。
2. 作为同一会话的后续参与者，我希望该会话继续使用已固定的归属人，以符合按会话固定的业务约定。
3. 作为历史会话的使用者，我希望下一次发言就能补齐归属人，无需重建会话。
4. 作为尚未再次发言的历史会话使用者，我希望会话仍沿用数字人创建者、再回退修改者的既有规则，不因本次升级中断。
5. 作为同时发言的参与者，我希望并发请求最终只固定一位归属人，后续请求不能覆盖。
6. 作为等待上一轮完成的参与者，我希望有效发言即使排队，也能在归属人为空时固定身份。
7. 作为重试请求的使用者，我希望重复提交不会变更归属人或重复创建入站消息。
8. 作为提交失败的使用者，我希望消息校验、附件绑定或事务失败时，不留下单独生效的归属人变更。
9. 作为平台管家会话使用者，我希望原有 Owner 身份绑定和权限上限保持一致。
10. 作为钉钉、飞书渠道使用者，我希望既有身份解析保持一致，即使会话意外存在归属人值也不采用它。
11. 作为管理员，我希望修复复用现有字段，不需要增量迁移、数据批量回填或历史评论改写。

## 实现决策

- 只改变工单澄清渠道。身份来自服务端认证上下文，前端请求不能指定他人的归属人。
- 复用会话现有可空的 `owner_user_id`，表示固定的澄清沟通责任人。保留现有数据模型、插入和读取映射。
- 在有效发言的事务中确定归属人；采用限定租户、会话、工单澄清渠道且归属人为空的条件写入。首次写入成功后不可覆盖。并发竞争后，以持久化结果为准，不把当前请求用户直接当作获胜者。
- 沿用已有会话锁、队列、消息幂等、事务与附件校验机制。归属人须在本轮能力准备和令牌签发前可见，排队和恢复时使用同一持久化身份。
- 只有工单澄清渠道的有效归属人优先于数字人创建者；归属人缺失时沿用创建者、再修改者的回退顺序。平台管家继续要求有效 Owner，钉钉、飞书等渠道保持既有解析。
- MCP 评论入口继续使用认证得到的 `context.userId()`，不单独伪造评论作者、不新增客户端身份参数。权限校验使用所签身份，因此实际可用权限以归属人在工作空间中的既有权限为准。
- 不新增表、字段、索引或迁移脚本，不连接或写入外部数据库。

## 测试决策与验收条件

复用已有服务测试和 Mapper 测试边界，不新增测试框架。测试验证身份及可观察结果，避免依赖私有实现。

| 场景 | 验收条件 |
|---|---|
| 澄清会话有有效归属人 | 能力准备签发归属人的令牌，即使数字人创建者不同或为空 |
| 澄清会话归属人为空 | 沿用创建者、再修改者回退；均缺失时保持失败 |
| 无归属人的会话首次有效发言 | 保存认证真人为归属人，本轮令牌使用持久化归属人 |
| 已有归属人再次发言 | 原归属人不变，后续令牌继续使用原归属人 |
| 历史会话再次发言 | 自动补齐，补齐前的历史评论不变 |
| 入站消息排队 | 同样能固定归属人；出队后使用固定身份 |
| 两人并发首次发言 | 条件更新仅一方成功；另一方不能覆盖且不能误用自身身份 |
| 消息或附件验证失败 | 不留下有效的独立归属人变更 |
| 重复客户端消息 | 沿用已有幂等结果，不重写归属人 |
| 无效或缺失发言人 | 在可信入口拒绝，不能写入无效归属人 |
| 平台管家 | 有 Owner 使用 Owner，无 Owner 仍失败，原令牌上限保持 |
| 钉钉、飞书 | 继续使用数字人创建者/修改者，忽略意外的 Owner 值 |
| SQL 边界 | 条件写入限定租户、会话和渠道，并含 `owner_user_id IS NULL` |

正式验证通过项目规定的生命周期入口执行与本次修改相关的最小测试和回归，并记录命令、退出码、实际通过和失败计数；若环境阻塞，准确记录未验证项，不把静态检查当作运行通过。

## 范围外

逐轮发送人字段、平台管家分享者身份变化、钉钉或飞书账号映射、前端显示改造、会话归属人变更入口、批量回填、历史评论改写、权限扩张、Git 提交推送、部署及外部数据库执行。

## 补充说明

前序调研提出的消息发送人字段和迁移方案属于按轮次设想，已被用户确认的按会话固定方案取代。首次发言的定义为通过现有校验并成功提交事务的入站消息；并发时按条件写入实际成功的一方确定，不以浏览器时间判定先后。

已有异常非空归属人不会自动修复或覆盖；该类数据需要另行核查。数字人生成评论内容的规则不变，改变的是会话 MCP 认证身份及由该身份决定的署名。
