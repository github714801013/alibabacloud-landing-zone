# 转真人按任务负责人规格

- 任务标识：`handoff-task-owner`
- 确认日期：2026-11-03
- 状态：用户已确认，适用于当前分支的本地二次开发
- 依据：用户逐项澄清确认；任务同步块已被 `workitem-scoped-repo-prep-spec` 消费。

## 问题说明

数字人自动转真人时，平台按显式 `to`、工单经办人、空间拥有人依次兜底，没有使用工单正文中已经声明的任务负责人。多任务工单会把真人转给工单经办人，而不是当前任务的实际负责人。

## 解决方案

转真人时解析 `contentMd` 中的任务同步块（当前载体为 `autowonder-jira-status`），按 `tasks[].aw_user_id` 取负责人：

1. 显式 `to` 属于任务负责人集合时采用 `to`（数字人已按当前派发仓库匹配 `tasks[].repos` 选择）；
2. 否则取第一条 `included=true` 且 `aw_user_id` 有效的任务负责人；
3. 无同步块、无任务或负责人无效时沿用原规则：显式 `to` → 工单经办人 → 空间拥有人；
4. 候选逐个校验工作区成员资格，第一个有效者生效。

任务来源不限 Jira；只要同步块含 `tasks[].aw_user_id` 即可。`jira_assignee` 是外部账号，不做映射。

## 用户故事

1. 作为数字人，我希望自动转真人时转到任务负责人，而不是工单经办人。
2. 作为多任务工单参与者，我希望按当前派发仓库匹配到的负责人接收转交。
3. 作为非 Jira 工单使用者，我希望只要正文有任务负责人声明就生效，不依赖 Jira 字段。
4. 作为平台管理员，我希望没有任务声明或负责人无效时保持原有回退行为。
5. 作为测试人员，我希望负责人解析和转交候选顺序都能被稳定验证。
6. 作为维护者，我希望新逻辑在独立文件，上游文件只做最小接入。

## 实施决策

1. **生效范围**：`REQUESTED_HUMAN`、`AUTOMATIC_HANDOFF_LIMIT`、`UNKNOWN_AGENT_FALLBACK_HUMAN` 三条转真人路径统一走候选链。
2. **负责人字段**：只认 `tasks[].aw_user_id`；缺省、非数字或非正数忽略。
3. **多任务**：显式 `to` 命中任务负责人集合时优先；未命中取第一条 `included=true` 的任务负责人。
4. **回退链**：任务负责人 → 工单经办人 → 空间拥有人（仅原有允许 owner 兜底的路径）；全部无效保持原错误码。
5. **仓库匹配**：由数字人按当前派发仓库匹配 `tasks[].repos` 后传 `to`；平台只做集合校验与兜底，不改仓库绑定。
6. **不改表结构、不新增依赖**：复用 `com.aliyun.autowonder.json` 解析。

## 验收标准

1. 自动转真人（目标数字人不可用/来回转超限）优先转给 tasks 第一条有效负责人。
2. 数字人按仓库匹配后传的 `to` 属于任务负责人集合时被采用。
3. 显式 `to` 不在任务负责人集合时纠偏为第一条。
4. tasks 为空或负责人非工作区成员时沿用原回退链。
5. 既有 `HandoffServiceTest` 全部通过。

## 不在范围

- 修改数字人绑定的仓库或平台侧做仓库匹配。
- Jira 账号到 AutoWonder 用户的映射。
- 改动数据库表结构、索引或新增依赖。
