## 1. 问题与目标

当前 DEV 在 `evidence/report.md` 的 `## e2e` 中自行声明端测场景，质量参差：出现过 `locators: 待 QA 在真实页面核对`、`assertions: 功能正常` 等无法执行或无法判定的写法。CR 没有统一的硬门禁，QA 在部署后才暴露声明缺陷，夜间无人值守时追责成本高。

目标是把“验收条件编号、e2e 声明、CR 评审、QA 验证”收敛到同一套判据：

1. 澄清阶段产出《验收条件与必测场景清单》，作为后续角色引用的唯一编号来源。
2. DEV 按清单声明 e2e 场景，声明必须可执行、可判定、可复现。
3. CR 按统一严重度判定 PASS/REJECT，PASS 必须输出覆盖结论。
4. QA 在部署后先核对声明质量；声明级缺陷退回 DEV，脚本级缺陷由 QA 修正。

## 2. 范围与非目标

**范围**

## 5. 变更设计

### 5.1 新增：验收条件与必测场景清单

**目标文件**：`dev-spec-gen/references/grill/interaction/acceptance-criteria-specs.md`

**读取入口**：10035 在 `grill-with-docs` 阶段执行：

```bash
reference-node-read --stage-id grill-with-docs --topic grill --path interaction/acceptance-criteria-specs.md
```

**产出规则**

- 产物命名：`<工单Key>-验收条件与必测场景清单.md`；无 Jira 输入时用 canonical `task_id`。
- 从需求正文、Jira 附件与澄清结论提取验收条件，原型图等附件已提供时一并核对；澄清阶段开发方案尚未产出时以需求为准，不阻塞。作为澄清定稿附件登记为正式产物；单文件、单版本，修改须覆盖旧版并写明变更点；不设 QA 确认门禁，后续角色直接按编号引用。
- 清单只描述验收意图与场景，不替代 e2e 脚本；脚本仍由 QA 在部署后编写。
- 编号为“验收 1..N”，不跳号、不与工单既有序号冲突。
- 每条至少包含：现象（一句话）、前置（数据/权限/环境，给具体值）、动作、可观测结果（条数/字段值/状态码/页面文本原文）、维度、覆盖层级、覆盖用例、数据可复用、数据准备；缺任一项视为不合格，不得交开发。
- 可观测结果禁止“正常/正确/无异常/符合预期”；文本或数值比对必须标判定方式：`=` 完全相等、`⊇` 包含、`~` 正则、多字段记命中数。
- 视觉或时序项标“（视觉）/（时序）”，并写明不进 e2e 断言。
- 七个维度：正向、逆向、边界、并发、一致性、权限、兼容回归；不适用写“不适用 + 原因”。
- 覆盖层级填写：页面e2e / 接口 / 接口+DB / 组件层 / 人工。
- 覆盖用例允许 1:N，用 `S7、T07` 形式；同一条件多个场景不得合并成一行。
- 数据可复用为“否”时，注明动作会改数据及失效条件；DEV 必须写 `depends_on`。
- 数据准备写“现成 / 需造（缺什么 + 谁 + 何时）/ 需提供（账号或环境 + 谁 + 何时）”；可多条，用“；”分隔。
- 涉及既有模块时检索该模块历史线上问题；命中的问题至少一条验收条件覆盖，并标注问题单号。检索使用 GitNexus/Jira（10035 已绑定 `jira-communication` 与 `oa_remote_gitnexus`，具备检索通道）；无命中、无权限或服务不可用时写原因，不阻塞。
- 条目上限 25 条；超过 25 条说明需求需拆单。少于 5 条不强行凑数，逐条说明为何不足。
- 清单缺失时的降级：DEV 按 `frontend-e2e-specs.md` 第 7 节第 10 条临时编号并标注“待对齐”；CR 记开放项，不阻塞；清单到位后统一重编号。

**与下游的契约**

- DEV 的 `## e2e` 映射表必须引用本清单编号，不得自造编号。
- CR 按编号逐条核对覆盖落点，缺项按 §5.3 的严重度处理。
- QA 按编号逐条报告验证方式（e2e 场景号 / 接口验证 / 接口 + DB / 组件层 / 未验证）。

### 5.2 修改：frontend-e2e-specs.md

**目标文件**：`dev-spec-gen/references/quality/frontend/frontend-e2e-specs.md`

在现有第 6 节之后新增两节。

#### 第 7 节 e2e 声明合格线（实现角色）

1. `## e2e` 之前必须有「验收条件 → 覆盖用例 → 状态」三列表；编号引用《验收条件与必测场景清单》，不得自造编号。
2. 每条验收条件至少对应一条用例；未覆盖写“本单不覆盖 + 原因”。清单写 `T08a、T08b` 时，映射表必须逐场景列出，不得合并成一行。
3. 每个场景四要素齐全：`page` / `case` / `preconditions` / `assertions`；`locators` 按第 7 条必须来自真实 DOM。缺一不得提交 CR。
4. `assertions` 必须可判定：条数、字段值、状态码、页面文本原文；按条件类型至少一种。出现“正常 / 正确 / 无异常 / 符合预期”即不合格。
5. 涉及文本或数值比对时，沿用清单的判定方式（`=` / `⊇` / `~` / 命中字段数），不得一律写死等断言。
6. 视觉或时序项（颜色、字号、倒计时、防抖间隔）不得写成 e2e 断言，须在场景下用 `not_asserted:` 注明“人工/截图复核”。
7. `preconditions` 必须给具体值（主键、编码、门店、会员号、样本文件名），禁止“存在相关数据”“数据已就绪”；`locators` 必须来自真实渲染 DOM，禁止“待 QA 在真实页面核对”这类占位，同页多控件须写作用域。
8. `target` 必须与已配置 target 的 `app.url` 主机完全匹配；同一 `## e2e` 块只允许一个 target；不写登录步骤、不写账号密码。
9. 清单里“数据可复用=否”的条件，必须在场景下写 `depends_on:`，用逗号分隔场景编号，说明与哪个场景串行、为何不可重跑。
10. 清单缺失时，DEV 可按工单条件临时编号并标注“待对齐”；CR 记开放项，不阻塞；清单到位后统一重编号。

#### 第 8 节 QA 声明质量前置核对（部署后测试）

1. 执行前按第 7 节核对声明；定位器与实际页面不符的，以实际页面为准修正并在报告中记录差异。这属于脚本级缺陷，由 QA 处理。
2. 场景缺失、断言不可判定、判定方式缺失、前置不明时，不得自行增补或改写验收断言：按 10030 步骤 10105「失败、交接及恢复」的分流规则交 `AW_FS_DEV` 补声明，并经增量 CR。
3. 脚本级缺陷——定位器失效、等待不稳、断言语法或实现错误——由 QA 按第 5 节失败定位流程修正，不交 DEV。
4. 为避免阻塞而用真实浏览器兜底补测时，必须在 `## 覆盖范围` 单列“声明缺失，已人工兜底，未纳入 e2e 回归”，且不计入 e2e 通过数。
5. `## 覆盖范围` 必须分三档写全：Mock 已覆盖 / 真实只读已验证 / 未验证项及原因；无缺口写“无”，不得留空。
6. 报告必须逐条列出本单验收条件编号与对应验证方式（e2e 场景号 / 接口验证 / 接口 + DB / 组件层 / 未验证），缺项即视为该条未完成。

**去重约定**：第 8 节第 5、6 条是覆盖范围与验收映射的唯一展开处；10030 步骤 10112 只引用本规范，不再重复全文。

### 5.3 新增：e2e 声明与验收映射评审

**目标文件**：`dev-spec-gen/references/quality/testing/e2e-review-specs.md`

**PASS 硬条件**

1. 映射表编号与《验收条件与必测场景清单》一一对应；清单里每条条件都必须能在映射表里找到落点（含 1:N 多场景）。
2. 按 `frontend-e2e-specs.md` 第 7 节逐条核对，不在此复述；该节的合格线即本评审的检查清单。
3. 出现以下任一情形判 REJECT（可修复，退回补声明，不关闭工单）：
   - 断言含“正常/正确/无异常”类措辞；
   - locator 写“待 QA 核对”；
   - 前置写“存在相关数据”；
   - 条件标“数据可复用=否”却无 `depends_on`；
   - 有页面级条件却声明“无 e2e 覆盖”且无理由；
   - 清单条件无落点且未说明原因或责任角色；
   - 清单已存在但映射编号无法对齐。
4. 缺覆盖但有明确理由或责任角色，或非页面级条件已由接口/组件层覆盖并列出编号，记为开放项，不判 REJECT。清单整体缺失时按 §5.1 降级，记开放项，不按 REJECT。
5. PASS 时评审结论必须写出固定句式：

```text
e2e 场景 N 条，对应验收 X/Y/Z；剩余 M 条由组件/接口层覆盖（列编号）
```

`M=0` 时写“剩余 0 条”。缺这句视为评审未完成。

6. REJECT 结论必须写明：退回项、责任角色（DEV 补声明 / QA 补脚本 / 澄清补清单）、是否阻塞。

#### 记忆 1：e2e 声明不合格样例集

只存具体反例与正确写法，不重复 §5.2 的规则全文：

- `assertions` 写“功能正常 / 显示正确 / 无异常 / 符合预期”。
