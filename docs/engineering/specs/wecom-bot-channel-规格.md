# 企业微信智能机器人渠道

## 问题陈述

AutoWonder 当前只有钉钉、飞书渠道。采用企业微信的工作区无法在群里与数字人对话，也无法选择企业微信接收平台通知。管理员需要在原有平台设置、工作区集成、个人资料和通知偏好中完成配置，避免另起一套服务。

## 解决方案

增加全局单选的 WECOM 渠道，使用企业微信智能机器人 WebSocket。群聊和通知各配置一个 BotID、Secret；平台管理凭据，工作区管理员将群与数字人绑定并明确委托其限定能力。群内文本由数字人异步处理，最终以 Markdown 回复原群。个人通知依赖接收者先与通知机器人互动，资料页准确提示该限制，保存身份不自动发测试消息。

## 用户故事

1. 作为系统管理员，我希望选择企业微信渠道，以便沿用现有渠道切换和准入机制。
2. 作为系统管理员，我希望分别配置群聊与通知机器人，以便隔离两类身份及生命周期。
3. 作为系统管理员，我希望留空 Secret 时保留原密文，以便安全编辑非敏感配置。
4. 作为系统管理员，我希望看到真实鉴权、连接及错误状态，以便区分配置保存与连接成功。
5. 作为工作区管理员，我希望将群绑定到可用数字人，以便群消息只进入正确工作区。
6. 作为工作区管理员，我希望明确确认群成员将共享被委托的数字人能力及公开结果，以便授权含义可审计。
7. 作为工作区管理员，我希望启停、修改及删除绑定，以便旧路由和已撤销授权不能继续执行或回复。
8. 作为群成员，我希望通过“群信息”获取当前群 ID，以便管理员完成绑定且不暴露平台内部数据。
9. 作为群成员，我希望 @机器人发送文本并收到最终结果，以便在群内完成数字人协作。
10. 作为群成员，我希望同群对话共享上下文，以便连续协作；原发言人与执行主体分别保留。
11. 作为用户，我希望填写个人企业微信 userid，以便作为通知目标地址。
12. 作为用户，我希望知道需要先私聊通知机器人，以便避免将身份保存误认为通知可达。
13. 作为用户，我希望主动测试通知并查看最终投递结果，以便区分排队、成功、失败和结果未知。
14. 作为用户，我希望逐类开启默认关闭的企业微信通知，以便保留现有站内偏好。
15. 作为用户，我希望新通知保留接收者语言快照，以便重试期间语言变化不改写历史内容。
16. 作为运维人员，我希望一个机器人只有一个后端连接持有者，以便多个后端不会互相踢线。
17. 作为运维人员，我希望明确记录结果未知且不自动重发，以便避免发送确认丢失后重复通知。
18. 作为原有钉钉、飞书用户，我希望新渠道不改变既有配置、消息和通知行为。

## 实现决策

- 复用现有 provider 注册、平台配置、个人身份、会话、路由快照和回复投递状态。补齐实际消费者中的二元分支，不将 WECOM 默认当成钉钉或飞书。
- 两用途独立 BotID；配置使用 appKey 表达 BotID、加密 appSecret 表达 Secret，保留原用途隔离规则。固定官方 WSS 地址，测试通过本地协议替身注入端点；不引入新的通用 SDK 或服务。
- 沿用现有渠道持久化：平台配置直接写入 `platform_im_channel_config` 的 WECOM 两用途行；只新增与飞书 SHARED 同构的 `wecom_robot_binding`；`notify_pref` 追加 `wecom` 列。入站去重和原路由复用 `agent_conversation_turn`，回复复用其投递字段。DDL 以澄清确认中的 SQL 原文为基线，并与初始化 schema 保持一致。
- 连接单活使用现有 Redis：按 botId 的 `setNx` 租约键与 TTL 心跳，值为实例令牌；失租停止收发；被踢进入退避，不立即抢连。只有有效持有者处理对应出站任务。鉴权、心跳及请求响应关联均使用真实协议。
- 消息回调无官方创建时间字段，使用接收时间与连接捕获的 selection generation 进行准入；外部消息键为 `WECOM:<botId>:<msgid>`，命中 `agent_conversation_turn.uk_external_msg` 排重；原路由和发言人写入 `source_context`。
- 文本入站，不新增附件或中途流式展示。未绑定群和不支持消息不发起数字人任务。“群信息”只返回当前群 ID。普通消息回复窗口为接收后24小时；超窗明确失败，不自动改成主动补发。
- 群绑定管理员显式委托本人在该工作区的限定能力，后端记录主体；创建或重授权需 authorizationConfirmed，不能提交任意平台 userId。能力准备和 MCP 调用校验原路由及当前成员权限，撤权、改绑、停用均失效。通知地址绝不作为真人认证来源。
- 每个群绑定拥有共享会话，外部发言人保存在原消息上下文，执行主体通过逐轮持久化及令牌绑定审计。
- Markdown 按 UTF-8 字节上限分片，不截断字符；部分发送成功后出错不得安全重发整个内容。官方 req_id 不保证幂等，写后超时/断线、过期 SENDING 均 UNKNOWN；只有确定一帧都未提交的暂态失败才可回队。
- 通知继续使用现有 Redis Stream 与 worker，不新增企微投递表。WECOM 任务只由 NOTIFY bot 连接持有者发送；企微发送结果未知时写入现有 DLQ 并 ACK，防止再次投递。接收者语言、地址与配置版本沿用现有任务字段。测试通知返回 deliveryKey/status（Redis 标记），仅本人查询。
- 绑定 CRUD、新通知配置、个人身份和偏好沿用既有接口风格；错误、乐观锁、工作区权限、系统管理员权限及密文回显遵循原项目契约。

## 数据流向与变动

- 群消息 → 当前连接及渠道准入 → 入站去重与群授权快照 → 数字人会话 → 原路由校验 → 持有连接的后端回复 → 持久化投递结果。
- 平台事件 → 通知偏好与接收者语言快照 → 现有 Redis Stream → NOTIFY owner 发送 → 协议确认；结果未知写 DLQ 并 ACK。
- 配置提交 → 加密存储与版本更新 → 连接租约协调 → 真实连接状态 → 脱敏页面展示。
- 配置载体：两渠道枚举和二元分支 → 显式支持 WECOM；平台配置新增两条用途记录，不保存明文凭据。
- 群聊载体：无企微绑定 → 新增 SHARED 绑定表；原消息、路由与授权快照复用会话回合的 `source_context`，排重复用 `external_msg_id` 唯一键。
- 投递载体：无企微连接归属 → Redis bot 租约；通知结果复用现有队列与 DLQ 表达，不新增投递账本。
- 个人载体：无企微通知选项 → userid 地址及默认关闭的 wecom 偏好；不改用户原有站内选项。
- SQL 完整设计原文在已确认澄清记录的“SQL 设计原文”小节；实现迁移与初始化 schema 逐项对应，本规格不复制第二份以免漂移。

| 页面/元素 | 交互动作 | 默认状态 | 显示/隐藏条件 | 触发/切换时机 | 结果与反馈 |
| --- | --- | --- | --- | --- | --- |
| 平台渠道选择 | 选择企业微信保存 | 保留原 provider | 系统管理员管理 | 保存成功刷新 selection 和相关缓存 | 失败保留原渠道，不本地提前切换 |
| 群聊/通知配置 | 两用途填 BotID、Secret、启停 | 未配置禁用；Secret不回显 | 系统管理员可编辑 | 保存后协调启停、轮换 | 保存与连接状态分开；空Secret保留原值 |
| 工作区绑定 | 新建、编辑、启停、删除 | 空列表 | 当前企业微信；非ADMIN只读或按现有权限隐藏写操作 | 提交授权确认，成功刷新版本 | 显示群ID获取说明、委托主体和群公开含义；未就绪禁用新建 |
| 连接状态 | 查看 | 未连接不能显示已连接 | 配置摘要展示 | 后端状态变化轮询刷新 | 与积压、失败、UNKNOWN分别展示 |

## 测试决策

用户确认开始实现并接受推荐方案，按公开边界进行行为测试，不测试私有方法或复刻实现。

1. 平台配置及绑定接口：验证校验、密文保留、用途身份隔离、显式委托、租户与版本冲突，参考现有共享群配置与绑定测试。
2. WebSocket协议边界：本地服务替身校验订阅、心跳、文本回调、req_id回复、断连和被踢；已写出无确认必须 UNKNOWN。
3. 会话与通知投递边界：验证消息重复、旧路由/撤权、双节点归属、过期租约、终态重放、通知语言快照和24小时边界。
4. 前端组件/API边界：验证第三provider选择、BotID表单、授权确认、身份测试状态、偏好默认值与双语。
5. 复用澄清测试数据基线逐条执行。真实企微数据当前未覆盖，本地替身不能宣称真实机器人联调通过。
6. 使用项目唯一 Community lifecycle 入口构建启动并完成 --check；不提交真实消息、不部署、不更改现有真实配置。

## 范围之外
