# 按工单声明范围准备仓库规格

- 任务标识：`workitem-scoped-repo-prep`
- 确认日期：2026-10-31
- 状态：用户已确认，适用于当前分支的本地二次开发
- 依据：工单正文 `autowonder-jira-status` 同步块、无关重仓预装阻塞现场、用户逐项澄清确认。

## 问题说明

派发任务包进入准备阶段时，平台把工单绑定的全部 WRITE 仓库都标为 `eager`，执行器会预克隆所有仓库。工单实际只涉及少数仓库时，无关的大仓库会拖慢准备阶段，甚至在网络或磁盘压力下阻塞派发。工单正文其实已有需求澄清阶段产出的机器可读仓库声明，但装配层没有消费它。

## 解决方案

工单装配时解析 `contentMd` 中的 `autowonder-jira-status` 同步块：只有 `included=true` 且 `repos` 非空的任务所声明的仓库标为 `eager`，其余 WRITE 仓库保持 `lazy`；没有有效声明时保持现状，全部 WRITE 仓库 `eager`。异常声明由 lazy 按需加载兜底，不阻塞派发。

## 用户故事

1. 作为工单责任人，我希望只预装本工单声明范围内的仓库，无关仓库不占用准备时间。
2. 作为执行器，我希望准备阶段只克隆工单真正需要的仓库，降低网络和磁盘压力。
3. 作为平台管理员，我希望没有声明块的工单保持现有行为，不因本次改动出现回归。
4. 作为需求澄清员，我希望同步块是仓库范围的唯一机器可读来源，不需要再维护第二份声明。
5. 作为全栈开发，我希望未声明的仓库仍可按需 lazy 克隆，并且 `allowCommit`/`allowPush` 权限不因准备模式改变。
6. 作为运维人员，我希望声明了但未绑定、重名或只读的仓库有明确 warn，不静默改变行为。
7. 作为测试人员，我希望收窄规则能在工单装配和仓库组装两个层面被稳定验证。
8. 作为会话能力包使用者，我希望本次改动不影响会话能力包的仓库准备行为。
9. 作为定时任务使用者，我希望定时任务的仓库快照行为保持不变。
10. 作为平台智能体使用者，我希望平台智能体的全租户只读 lazy 行为保持不变。
11. 作为非 Jira 工单使用者，我希望没有同步块时回退现状，不被错误地全部 lazy。
12. 作为适配器维护者，我希望工单标题只要求包含父需求编号，不再强制 `[父需求编号]` 前缀。
13. 作为需求澄清数字人，我希望线上职责与新适配器规则一致，非 `[key]` 标题也能触发同步台账。
14. 作为代码评审，我希望实现只消费已经确认的范围，不引入新的平台字段或表结构。
15. 作为后续维护者，我希望规则有明确日志和测试边界，出现异常声明时能快速定位。

## 实施决策

1. **数据源**：只消费 `contentMd` 中的 `autowonder-jira-status` 块；不新增平台字段、表结构或 MCP 工具。
2. **收窄条件**：`tasks[]` 中 `included=true`（缺省视为 true）且 `repos` 非空的任务，取其仓库名并集标 `eager`；其余 WRITE 仓库 `lazy`。
3. **回退条件**：无块、块不可解析、无 `tasks`、所有 `repos` 为空或缺失时，回退全部 WRITE 仓库 `eager`，并记 warn。
4. **`included=false`**：其 `repos` 不计入 eager 集合。
5. **`scope_confirmed`**：装配侧不校验该字段；即使为 false 也按块内容执行，异常范围由 lazy 按需加载兜底。
6. **名称匹配**：忽略大小写与首尾空白；未命中、命中多个或命中非 WRITE 绑定只记 warn，不阻塞，不引入 repoId。
7. **权限字段**：未声明仓库仍保持 `allowCommit=true`、`allowPush=true`（按 WRITE 绑定），只改变 `mode`。
8. **装配范围**：只改工单装配路径；会话能力包的三参仓库组装、定时任务快照、平台智能体的全租户仓库组装均不变。
9. **适配器配套**：独立技能仓中的状态同步规则改为“标题包含父需求编号（不要求格式）”；线上数字人职责同步更新。
10. **不改表结构**：`workitem` 行没有通用 metadata JSON 字段，`tags` 是标签语义，不能作为仓库声明载体。

## 测试决策

- 只验证外部行为：给定工单正文、绑定仓库与权限，断言输出 `repos[].mode`、`allowCommit`、`allowPush`；不测试私有解析细节。
- 测试 seam：
  - `PackageContextAssembler.assembleWorkitem`：工单装配端到端，覆盖块解析到最终仓库模式。
  - `PackageContextAssembler.buildRepos` 四参重载：规则边界，覆盖 included、空 repos、大小写、未命中/重名/只读、权限字段。
  - 适配器 `confirm_document` / `validate_workitem`：标题包含父需求编号的通过/拒绝行为。
- 必测用例：有块且 included repos → 精确 eager；`included=false` 忽略；空/缺失 repos → 全 eager；坏块/无块 → 全 eager；大小写与首尾空白；未命中/重名/只读 warn；权限字段不变；平台/会话/定时路径不变。
- 先例：`PackageContextAssemblerTest` 已有工单声明范围的同类测试；适配器 `tests/test_jira_status_sync.py` 已覆盖标题与台账规则。

## 范围外

- 会话能力包、定时任务、平台智能体的仓库准备策略。
- 执行器侧固定目录 + worktree 复用优化。
- 工单-仓库一等公民关联表、平台 JSON 字段或新 MCP 工具。
- 非 Jira 工单的仓库声明（仍写在澄清文档中，不回退为块）。
- 工单文档正文的解析。
- 执行器 lazy 仓库首次克隆失败的补偿（由现有 prepare 重试覆盖）。
